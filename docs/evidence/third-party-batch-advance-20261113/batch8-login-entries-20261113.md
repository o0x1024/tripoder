## 2. 哔哩哔哩：同意隐私后客体 FATAL

这是本批唯一的崩溃，也是这批应用里第一个「启动成功、首屏可达，但在穿过隐私门槛时死掉」的实例：

```
11-13 19:19:29.704 28536 28536 E AndroidRuntime: FATAL EXCEPTION: main
11-13 19:19:29.704 28536 28536 E AndroidRuntime: Process: tv.danmaku.bili, PID: 28536
```

同轮 `topResumedActivity` 从客体 `TaskP3$F0M1C2` 回落到 `WorkbenchActivity t16525` —— 客体进程死亡，会话退回 Workbench。

### 复现轮没拿到栈，但暴露了一个更值得注意的现象

复现脚本 `/tmp/bili_crash.sh`（冷启动 → 等 30s → 点「同意并继续」→ 抓全量 crash 缓冲）这一轮里：

- Workbench 状态栏显示 **`启动应用「哔哩哔哩」 · 已完成`**
- 但同一次读数的 `topResumedActivity` 是 **`WorkbenchActivity t16529`**，不是客体 Activity
- `+30s` 时点向页面点「同意并继续」返回 `NOT_FOUND`（因为前台根本不是 bili 的隐私页）

即：**引擎把这次启动判定为「已完成」，而客体 Activity 并不在前台**。两种可能与实录一致，均未在本轮分辨：

1. 客体起来后立即死亡（与上一轮同意后崩溃同源，只是死得更早），临时。
2. 客体 Activity 起来了但没拿到 resumed 状态（容器焦点/任务栈问题）。

分辨方法很明确：在 `+10s / +20s / +30s` 三个时点各读一次 `topResumedActivity` 与 `ps`，并对 `am_proc_died` 按 `:slotN` 名字取样（按包名查会得到空结果，见 `guest-proc-name-is-slot`）。本轮没做，所以不主张是哪一种。

### 完整栈是当前唯一的缺口

本轮 crash 缓冲里只有 `FATAL` 与 `Process:` 两行 —— 因为抓取命令用了 `grep -E 'FATAL|Process: |Caused by' | head -4`，栈帧行（`at ...`）与异常类型行都不在匹配集合里；复现轮又因上述启动异常没能重放。因此：

- **未能判定**这次崩溃是容器门面缺陷（`dev.tripoder.runtime.*` 帧）还是 bilibili 自身（原生层/线程断言）。
- 按既有判据（`stack-attribution-rule-refined`、`facade-must-honor-platform-exceptions`），归属必须靠完整栈里的帧来判断，**不能**先假定是应用不兼容。

## 3. 边界

- 「入口已定位」= 页面上存在可点的登录控件并已取到 bounds；**没有**点击登录、没有走完登录闭环。滴滴/今日头条/支付宝三个应用的实际登录仍未验证。
- 闲鱼与淘宝的「同意」点击命中了文本，但页面未推进 —— 可能命中的是同意条款里的文字而非按钮本身，也可能是二次确认页。**未区分**。
- 携程同意后 `login-ish` 过滤为空，只说明该页没有「登录/手机号/我的/首页/推荐」这些字样，不说明它是失败页。
- 唯品会的失败是**取证手段**失败（dump 文本被截断成 `同`，`guest_ui.py tap` 精确匹配落空），不是应用缺陷。正确做法是从 dump 取 bounds 直接按坐标点，而不是猜文案。
