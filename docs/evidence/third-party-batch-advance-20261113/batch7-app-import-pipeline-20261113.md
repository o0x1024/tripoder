# 第 7 批 · 批量导入的失败点不是选择，而是提交按钮的文案是动态的

- 设备：`d861a4fa`，构建 v70（诊断构建，与导入无关）
- 对象：Workbench「添加应用」（容器内应用集合的入口）
- 结论：**导入流程本身是好的**，blocker 是自动化脚本按固定文案点提交按钮。
  修正后每应用约 40 秒，`CATALOG_READY installs` 逐次 +1。

## 1. 现象与误判

自动化脚本按「搜索 → 点应用格子 → 点『选择要添加的应用』」执行，结果：

| 观测 | 当时的推断（**错的**） |
|---|---|
| `已选 0 个` 一直是 0 | 应用格子点不中 |
| 仍然显示「添加完成 · 成功 7 个」 | 上一个批次的残留，说明这次没导入 |
| `installs=21` 不变 | 导入全部失败 |

## 2. 真正的原因（两条，都读过代码/实测过）

1. **提交按钮文案随选中数变化**。`WorkbenchActivity` 的导入条：
   零选时按钮是 `选择要添加的应用`，一旦有选中就变成 `添加所选 N 个应用`。
   脚本按固定文案点，选中之后那一次点击就没有目标 —— 表现为「什么都没发生」，
   而横幅仍是上一轮的「添加完成 · 成功 7 个」，极易被当成「导入成功但列表没刷新」。
2. **点应用格子不是可靠的选择方式**；`全选` 是可靠的。选中后 dump 里
   `已选 1 个` / `Button 取消全选` 同时出现，这是「已选中」的判据。

## 3. 可复现入口

`android/scripts/import_apps.sh`（本轮新增）：

```bash
bash android/scripts/import_apps.sh com.eg.android.AlipayGphone com.taobao.taobao
```

每个包独立一次 `force-stop` → `重新连接`×2 → `添加应用` → 搜索 → `全选` →
**从 dump 里抓 `添加所选 N 个应用` 再点** → 读 `CATALOG_READY installs`。
每个应用都从干净进程开始，避免上一次的选中状态跨轮泄漏（泄漏时 `全选` 会变成 `取消全选`，
脚本就会拿到 `NO_SELECTION`，这是可诊断的失败而不是静默失败）。

实测（v70，连续三包）：

```
--- taobao.taobao label=[添加所选 1 个应用]   CATALOG_READY installs=23
--- xingin.xhs   label=[添加所选 1 个应用]   CATALOG_READY installs=24
--- zhihu        label=[添加所选 1 个应用]   CATALOG_READY installs=25
```

（起点 22 = 原有 21 + 支付宝，支付宝为同一流程的首次验证：「添加完成 · 成功 1 个」，
列表项变为「支付宝，已在此空间」。）

## 4. 边界

- 只验证了 `--scroll` 列表 + 搜索过滤 + `全选` 这一条路径；未验证
  「不搜索、直接在长列表里点单个格子」是否也可靠。
- 导入是安装事务（APK 复制/校验），本轮每次等 14 秒就够，但大包（抖音级）需要更长等待。
- 应用集合的容量与进程槽位（`RuntimeSlot.CAPACITY=8`，按**进程**计）是两件事：
  导入多少不影响槽位，同时**运行**几个才影响。
