# 替代登录路径评估（原生引导 / Web 版 / 开放平台 OAuth）

- **日期**：2026-11-12
- **关联**：[P2 来源能力矩阵](guest-provenance-capability-matrix.md) §4.1 · [身份与来源契约](identity-provenance-contract.md) §6 · [Guest 兼容性](guest-compatibility.md) §3.4/§3.5
- **要回答的问题**：容器内抖音 App 的登录被服务端拦截框架拒绝之后，产品还能给用户什么？

---

## 0. 先把两个目标分开

不分开必然选错方案——三条候选路径覆盖的是两个完全不同的目标：

| 目标 | 内容 | 需要的凭证 |
| --- | --- | --- |
| **T1** | 用户要在 Tripoder 里**使用抖音客户端**（刷、搜、发布、私信…） | 抖音 App 在容器内的**登录态** |
| **T2** | Tripoder（或第三应用）要**拿到抖音用户身份**（登录自己的账号体系、调用开放能力） | `openid` + `access_token`（开放平台签发） |

T2 的凭证与 T1 的登录态**互不兑换**。任何「用 OAuth 让容器内 App 登录」的设想都跨了这条线。

## 1. 第一性原理：登录态由三样东西组成

1. **客户端身份**（包名 / 签名 / 版本码）——可投影，且已实测与原生逐列一致（A/B 举证表）。
2. **运行环境指纹**（UID 归属、`/proc` 与 data 目录属主、provider authority 属主）——**不可投影**，契约 §6.1 已登记为永久差异。
3. **服务端签发的会话绑定**——把 token 绑到「这次客户端 + 这次渠道 + 这台环境」。它在服务端，**本地既不可投影也不可改写**。

**推论**：T1 的登录态只在两种情况下能拿到——环境是真的（原生安装），或服务端不要求环境（Web / 开放平台通道）。这两条正是下表的 B 与 C，而 A 是「承认第一条、把用户送过去」。

## 2. 路径判定

| 路径 | 覆盖 | 判定 | 成本 | 前置依赖 | 证据强度 |
| --- | --- | --- | --- | --- | --- |
| **A 原生环境登录引导** | T1（用户自己用原生） | ✅ 可行，今天就能上 | S | 无 | 已实测（本机同账号原生登录页无拦截） |
| **B 容器内官方 Web 版** | T1（Web 功能子集） | ✅ 可行（需一次风控实测） | S–M | 无资质要求 | 外部事实 + **未实测** |
| **C 开放平台 OAuth** | T2 | ✅ 可行，需资质 | M | 企业资质 + 应用审核 + scope | 官方文档（external） |
| **D 扫码会话注入容器 App** | T1 | ❌ 不可行 | — | — | 推论（服务端绑定 + 契约 §6.4 红线） |

### 2.1 A：原生环境登录引导

**事实基础**：对照组实测（设备 d861a4fa，同机、同账号、同网络）——原生抖音登录页正常渲染，无任何拦截弹窗 ⇒ 设备级与账号级风险标记已被排除，限制只发生在容器环境。

**做法**：宿主在客体返回 block 类错误码时，给出一条明确出口——「在系统桌面使用官方版本登录」，并附一次直达系统抖音的启动（`Intent` 指向系统的 `com.ss.android.ugc.aweme` 启动器，而不是容器内的实例）。

**局限（必须对产品说清）**：登录态留在原生 App 里，**容器内的抖音依旧未登录**。A 不解决 T1，它解决的是「用户卡死 + 产品边界被误解成缺陷」。

**成本 S**：一段文案 + 一个跳转 + 错误码识别。文案直接取矩阵 §4.1，禁止出现「升级后可用」。

### 2.2 B：容器内官方 Web 版（唯一「不离开 Tripoder 又能登录」的路径）

**机理**：抖音 Web 端（`www.douyin.com`）自己提供官方扫码/手机号登录，走的是**官方 Web 端的风控通道**，不经过 App 的渠道校验——容器在这里只扮演浏览器，不需要投影任何 App 事实。

**能力子集**：浏览、搜索、部分互动与私信（以 Web 端当前实现为准）；**不含** App 独占能力（如部分发布形态、开播、App 内小程序）。

**成本 S–M**：独立入口 + 独立 WebView 配置（Cookie/存储与客体隔离）+ 登录态持久化（属宿主账号体系，不属客体）。

**未验证**：容器 WebView 的内核指纹是否会触发 Web 端风控——**上产品前必须实测一次**（见 §5 第 1 条）。

### 2.3 C：抖音开放平台 OAuth

**官方事实**（developer.open-douyin.com，网站应用「手机号和扫码登录授权」）：抖音登录是基于 OAuth2.0 的授权码模式；网站应用**目前提供扫码登录授权**，用户在抖音 App 内扫码确认后回调 `code`；移动应用可接 open SDK 拉起抖音 App 授权。前置条件是**创建应用并通过开放平台审核、配置授权回调域、申请对应 scope**。

**拿到什么**：`code → access_token`，以及 `openid`——即「该用户在你的应用中的身份」。**不是**抖音 App 的登录态。

**判断**：C 只满足 T2。若产品要做「用抖音账号登录 Tripoder 自己的账号体系」「读取用户授权的公开信息与内容管理」，这是正规且稳定的路，与容器无关，也不需要容器任何改造。

**成本 M**：资质与审核周期、服务端换取/刷新 token、隐私告知（授权范围与用途）。

### 2.4 D：把扫码得到的会话注入容器内 App — **不做**

扫码登录建立的是「抖音 App ↔ 抖音 Web 端」的会话，服务端会把会话绑到发起端（域名、UA/JS SDK 签名、设备侧指纹）。把它搬去充当容器内 App 的会话，等于伪造服务端签发上下文——与契约 §6.4「不得向第三方谎报安装来源」同一类越界，且技术要求上也不成立（密钥与绑定在服务端）。

## 3. 推荐顺序

1. **B**（若产品要「在 Tripoder 内用抖音」）：立即可做，先做一次 WebView 风控实测。
2. **A**（无论是否做 B 都要做）：兜底与边界告知，配合已入库的降级文案。
3. **C**（若产品要「用抖音身份登录 Tripoder」）：独立立项，走开放平台资质，与容器解耦。
4. **不做 D。**

**取舍一句话**：T1 在容器内无解（判据在服务端，v46 已证伪本地归因），所以要么降低载体（B：Web 版），要么改变载体（A：原生）；T2 有正规通道（C），但它回答的是另一个问题。

## 4. 与已入库结论的一致性

- 矩阵 §4.1 的「登录路径降级」就是本文的 A；本文补上 B/C 两条**真正可用**的替代，并说明为什么「验证码登录」不在其列（2026-11-12 实测：容器内验证码登录同样被拦）。
- 矩阵 §4.2「直通模式不可行」仍然成立；**B 不是直通模式**——不安装官方包、不共享包身份，只承载 Web 会话。
- 本文不改变任何 P2 判定，也不引入新的投影需求。

## 5. 待验证（诚实标注，勿当成结论）

1. 容器 WebView 访问 `www.douyin.com` 的扫码登录是否触发 Web 风控（**未测**，B 的放行条件）。
2. 抖音 Web 端当前的可用能力子集（随官方调整变化）。
3. 开放平台对 Tripoder 这类应用的资质与审核结论（**未申请**）。
4. 移动 open SDK 在容器内能否拉起（若客体内集成；**未实测**）。
